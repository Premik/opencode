# Overview

opencode is a monorepo (managed with Bun workspaces + Turborepo) for an AI coding assistant and its surrounding platform. The project bundles a CLI, a terminal UI (TUI), a web app, a desktop app, shared core logic, an LLM abstraction layer, protocol/schema packages, and several SDKs.

Key architecture points:
- Multiple interfaces: a CLI/TUI (SolidJS + @opentui), a shared web app (`packages/app`, SolidJS), a desktop Electron wrapper (`packages/desktop`), and a plugin system (`@opencode-ai/plugin`).
- Core business logic and API server live in `packages/opencode`. The session runtime preserves durable conversational history while dynamically assembling system context (instructions, tool descriptions, user-defined context sources) for each provider turn.
- V2 separates concerns across packages: Schema (lightweight shared types), Protocol (API endpoint construction), Server (concrete HTTP handlers), Client (generated Promise/Effect APIs), and SDK (composed in-process host). The `HttpApi` is authoritative for public client capabilities.
- System Context is built from independently observed, stable-keyed Context Sources; changes sampled lazily at Safe Provider-Turn Boundaries (never pushed asynchronously). A Context Epoch spans one immutable baseline; compaction starts a new epoch.
- Client tiers: a zero-Effect Promise client (`@opencode-ai/client`) and an Effect-native client (`@opencode-ai/client/effect`). The SDK (`@opencode-ai/sdk-next`) composes client, core, and server in-process without network I/O.

## Root (REFINED)

- `AGENTS.md` — Comprehensive contributor guide covering branch naming (max 3 hyphenated words), conventional commit format (`type(scope): summary`), and detailed TypeScript style rules (inline logic, avoiding `try/catch`, Bun APIs, functional array methods, Effect generator patterns, Drizzle schema snake_case, testing without mocks). Documents the V2 Session Core architecture rules for durable prompt admission, session execution ownership, location-scoped runners, delivery vocabulary (steer/queue), and system context organization.
- `CONTEXT.md` — Detailed domain glossary and architecture reference for the Session Runtime. Formally defines ~40 terms (System Context, Context Source, Context Epoch, Session Drain, Model Tool Output, etc.) with precise interrelationship rules, and documents the client-contract architecture (HTTP client generation, embedded vs. networked, SDK contract IR, emitter policies). Authoritative source for the V2 session model's vocabulary and invariants.
- `CONTRIBUTING.md` — Contributor guide covering dev setup, build commands, debugging techniques, and PR/issue policies. Explains monorepo layout, how `bun dev` maps to the built CLI, building a standalone executable, running against a different target directory, debugging with Bun `--inspect` (incl. VSCode config), and the trust/vouch system, issue templates, and PR expectations (issue-first, conventional commits, UI screenshots for UI changes).
- `README.md` — Top-level project README for OpenCode AI coding agent. Lists installation methods (npm, Homebrew, Scoop, pacman, Nix), desktop app beta downloads, custom install directory priority order, two built-in agents (build and plan) switchable via Tab, and links to docs, contributing, and community.
- `package.json` — Root Bun workspace config (1.3.14) spanning `packages/*`, `packages/console/*`, `packages/stats/*`, `packages/sdk/js`, `packages/slack`. Dev scripts: `dev` (CLI app), `dev:desktop`, `dev:web`, `dev:console`, `dev:storybook`, lint via oxlint, typecheck via Turbo, `postinstall` runs `fix-node-pty`. Notable deps: Effect (beta), Hono, Drizzle ORM, SolidJS, SST, Shiki, @opentui, with patched packages for AI SDKs, SolidJS, Effect, MCP.
- `sst.config.ts` — SST (Ion) infra config deploying OpenCode's cloud backend on Cloudflare (AWS secondary, us-east-1, stage-aware S3 protect/removal). Configures Stripe, Random, PlanetScale, Honeycomb providers. `run()` dynamically imports infra modules (`infra/stage`, `app`, `lake`, `stats`, `console`, `enterprise`, `monitoring`) conditional on stage and AWS features.
- `install` — Shell script for downloading/installing the OpenCode binary across Linux/macOS/Windows. Supports custom versions, local paths, `--no-modify-path`. Detects OS, arch (Rosetta-aware arm64 fallback), CPU feature level (AVX2 baseline for x64), musl libc (Alpine), platform archives. Downloads from GitHub releases with a curl-based progress bar, installs to `$HOME/.opencode/bin`, optionally modifies PATH in shell configs.
- `turbo.json` — Turbo repo task config defining `typecheck`, `build` (outputs to `dist/**`), and per-package `test` tasks for `opencode`, `@opencode-ai/core`, `@opencode-ai/app`, `@opencode-ai/ui`, `@opencode-ai/session-ui`. Global env passthrough: `CI`, `OPENCODE_DISABLE_SHARE`.

## packages/core/src/ (REFINED)

V2 core: durable session execution loop, system context algebra, built-in tools, plugin system with 31 provider facades, database/event infrastructure, and location-scoped service composition. All services are Effect-based with either `makeLocationNode` (location-scoped) or `makeGlobalNode` (process-global) lifecycle from `effect/`. SQL files define Drizzle tables with snake_case fields; several top-level files are pure re-export barrels for schema types.

**Session runtime** (`session/`):
  - `runner/` — Serialized V2 execution loop. `llm.ts` (core run loop: loads session -> selects agent -> initializes system context -> resolves model -> streams exactly one `llm.stream()` per turn, handles overflow compaction recovery, steer/queue input promotion at safe boundaries). `publish-llm-event.ts` (incremental event persistence for one provider turn, tracks tool lifecycle in `Map`, fragment streaming). `to-llm-message.ts` (projects V2 history -> canonical LLM `Message[]`). `model.ts` (catalog -> concrete model resolution, tagged errors). `index.ts` (barrel + `Interface`/`RunError`). `max-steps.ts` (step-limit prompt constant).
- `compaction.ts` — Auto-summarizes older messages when token budget exceeded (reverse-scan split point -> structured summary prompt -> LLM call). Defaults: 20K buffer, 8K keep.
- `context-epoch.ts` — Persisted System Context snapshot per session; `prepare` loads + reconciles epoch (Unchanged/ReplacementReady/Update), `reset` on move/revert.
- `input.ts` — Durable prompt admission/promotion lifecycle (`admit`/`promoteSteers`/`promoteNextQueued`); exact-retry reconciliation via `equivalent`/`matchesPrompt`. `LifecycleConflict` tagged error.
- `message-updater.ts` — Event-driven state machine building session messages from `SessionEvent` variants (immer-based immutable updates, in-memory + DB-backed adapters).
- `projector.ts` — Event projector: session events -> persistent DB state (handles V1+V2 events, revert deletion, move location update). Global node.
- `revert.ts` — Three-phase revert (stage/clear/commit) with file snapshot restore.
- `run-coordinator.ts` — Per-key execution serializer (joins same-session resumes, coalesces wakeups, concurrent across sessions, `FiberSet.makeRuntime`).
- `sql.ts` — Drizzle tables: Session/SessionMessage/SessionInput/SessionContextEpoch/Todo + V1 Message/Part (cascade-delete on session FK).
- Supporting files: `store.ts` (data access), `history.ts` (message loading/decoding), `info.ts` (row->typed struct), `todo.ts` (per-session todo items), `execution.ts`+`execution/local.ts` (process-global execution controller, `noopLayer` for headless), `schema.ts`/`prompt.ts`/`message.ts`/`event.ts` (schema re-exports), `error.ts` (tagged errors).

**Config** (`config/`): Top-level files are Effect `Schema` definitions per domain -- `agent.ts`, `provider.ts` (model+cost+limit+variants), `mcp.ts` (local/remote+OAuth+timeouts), `lsp.ts`, `markdown.ts` (frontmatter parser+sanitizer via `gray-matter`), `compaction.ts`/`formatter.ts`/`attachments.ts`/`reference.ts`/`command.ts`/`tool-output.ts`/`watcher.ts`, `experimental.ts` (policies), `plugin.ts`. `plugin/` subdir -- runtime loaders using `define()`: `agent.ts` (discovers agents from MD+JSON, merges permissions, V1 migration), `command.ts`, `external.ts` (npm/local plugins via `Npm.Service`), `provider.ts` (providers+models -> catalog + integrations), `reference.ts` (git/local sources), `skill.ts` (dir/URL sources).

**Built-in tools** (`tool/`): -- All follow: resolve path -> check `external_directory` permission -> assert action -> perform work -> return typed output. Each is a self-contained `makeLocationNode`.
- Foundation: `tool.ts` (`Tool.make()` constructs opaque `Definition`, WeakMap-cached `Runtime` with `settle()`), `registry.ts` (merges application + location-local tools, materializes with permissions), `tools.ts`/`application-tools.ts` (registration interfaces), `builtins.ts` (composition root, 12 tools).
- File tools: `edit.ts` (exact text replacement, stale-content guard via `writeIfUnchanged`), `write.ts` (create/overwrite, BOM-aware), `read.ts`+`read-filesystem.ts` (file/dir reading, 64KB magic-byte detection, image base64 <20MB, paginated text with 2000-char line truncation), `apply-patch.ts` (unified patch application, partial progress on failure).
- Search: `glob.ts` (ripgrep glob), `grep.ts` (ripgrep regex, grouped output format).

# Run/build

- **Monorepo manager:** Bun workspaces + Turborepo (`turbo.json`). Use `bun install` at repo root.
- **Type checking:** Run `bun typecheck` from package directories (e.g., `packages/opencode`), never `tsc` directly.
- **SDK regeneration:** After changing public Protocol or Server `HttpApi`, run `bun run generate` from `packages/client`. Legacy JS SDK: `./packages/sdk/js/script/build.ts`. Do not edit `src/generated` or `src/generated-effect` directly.
- **Tests:** Cannot run from repo root; run from package dirs like `packages/opencode`.
- **Default branch:** `dev` (not `main`). Use `dev` or `origin/dev` for diffs.
- **Standalone executable:** `./packages/opencode/script/build.ts --single` from repo root → `./packages/opencode/dist/opencode-<platform>/bin/opencode` (e.g. `darwin-arm64`, `linux-x64`).
- **Run against a different directory:** `bun dev <directory>` targets a different repo/directory than the default `packages/opencode`; `bun dev .` runs OpenCode against itself.
- **Debugging:** Most reliable is `bun run --inspect=<url> dev ...` from a terminal. Breakpoints may not work with `bun dev` (runs server in a worker thread); use `bun dev spawn` instead, or debug server and TUI separately with `--inspect` and explicit ports.
- **Web app dev:** Start the server first (`bun dev serve`), then `bun run --cwd packages/app dev` separately (Vite on port 5173 needs the API server running).
- **Pre-push hook:** `script/hooks` installs a `pre-push` git hook running `bun install` + `bun run typecheck`.
